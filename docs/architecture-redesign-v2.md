# Luvira AI DevFlow アーキテクチャ再設計 v2

## 決定

現行の「Issue コメント → 単一 GitHub Actions → AI 実行・Git 操作・PR 作成」の経路を段階的に廃止する。Issue は依頼の入口に限定し、承認・実行・品質判定・公開を分離する。

## 現行の構造的な問題

1. 単一の実行Workflowが認可、Secret Manager参照、AI実行、Git操作、PR作成を担い、権限境界がない。
2. Issue本文・コメントが仕様、実行命令、テスト注意書きを兼ね、自然言語の矛盾が結果を変える。
3. オーケストレーターは計画を返すだけで、状態の唯一の記録でも実行制御主体でもない。
4. 監視・品質・公開の根拠がActionsとコメントに分散し、再実行・重複課金・追跡を一貫して止められない。
5. 実行ワークスペースに認証補助ファイルとAI変更対象が共存し、成果物許可リストがない。

## 目標構成

```text
Issue Form → Control Plane → Execution Broker → Isolated Worker
           → Verification Plane → Independent Reviews
           → Publication Adapter → GitHub Ruleset / Human merge approval
```

### Intake

Issue Formは依頼内容、対象リポジトリ、リスク、受入条件を構造化して受け取る。コメントは会話・表示専用で、実行や承認の唯一の根拠にしない。

### Control Plane

不変のtask_idと仕様スナップショットのハッシュを発行し、状態、承認、予算、モデル、再試行、監査証跡の唯一の記録を持つ。

```text
DRAFT → VALIDATED → AWAITING_HUMAN_APPROVAL → AUTHORIZED
→ EXECUTING → VERIFYING → REVIEWING → AWAITING_MERGE_APPROVAL
→ PUBLISHED | REJECTED | FAILED | CANCELLED | EXPIRED
```

仕様・対象コミット・モデル・予算が変われば新規承認を必要とし、同一task_idの二重実行を禁止する。

### Execution Broker

実装AIにはGitHub管理、GCP管理、長期秘密情報、PR作成の権限を渡さない。固定された仕様・ベースコミット・作業領域だけを渡し、成果物は許可された差分と検証結果に限定する。認証情報を作業ディレクトリへ配置せず、未許可ファイル、バイナリ、資格情報、生成物は公開前に失格とする。

### Model routing

- 初手は評価済みの低コストOpenCode Goモデル。
- 高単価OpenCode Goモデルへの自動昇格は禁止。
- provider障害、上限、タイムアウトだけを退避対象にし、最大2回まで。
- テスト失敗、秘密情報検知、ポリシー違反では退避せず停止。
- Codex / Claude Code / Copilotへ実装を退避した場合、その実装者を同一PRのレビュー担当から除外。

### Verification / Review / Publish

公開前に、許可リスト差分検査、テスト、静的解析、依存関係・SBOM・脆弱性検査、秘密情報・生成物検査、仕様照合をfail-closedで実施する。

低コストモデル実装のPRは、CodexとClaude Codeの独立レビューを必須とする。別の認証ID、実行環境、会話コンテキストを用い、片方でも変更要求・失敗・判定不能なら停止する。

PR作成は検証・レビュー通過後に、専用の最小権限GitHub Appだけが行う。実装AI・レビューAIはPR作成・マージを行わない。マージはGitHub保護ルールと人間の明示承認を必要とする。

### 監視の4レイヤー

| レイヤー | 対象 | 許可 |
|---|---|---|
| 実行監視 | 利用量、障害、タイムアウト、退避回数 | 停止・記録のみ |
| 品質監視 | テスト、秘密情報、依存関係、成果物 | fail-closed判定・記録のみ |
| 独立性監視 | 実装者とレビュー者の分離 | レビュー無効化・記録のみ |
| 統制監視 | 承認、鍵、規則、監査証跡 | 停止根拠・通知のみ |

監視者にはコード変更、PR、マージ、権限変更、秘密値の閲覧を許可しない。修復は必ず別PRで通常の品質ゲートを通す。

## 移行計画

1. **Phase 0 — 凍結と棚卸し**: 旧経路の機能追加を止め、権限、秘密情報、Actions、Apps、保護ルール、監視ログを棚卸しする。
2. **Phase 1 — 制御プレーン**: 状態機械、仕様スナップショット、承認トークン、予算・再試行制御を実装する。この段階でAIは起動しない。
3. **Phase 2 — 隔離実行と検証**: AIを差分生成専用の隔離環境へ移し、公開せず検証結果のみ確認する。
4. **Phase 3 — 公開と独立レビュー**: Publication Adapterと二重レビューを接続し、検証済み差分だけをドラフトPR化する。
5. **Phase 4 — 旧経路停止**: 新経路の受入試験後、Issueコメントで直接AIを動かすWorkflowを停止する。

## 受入条件

1. テストIssueは構造化承認なしにAI利用枠を消費しない。
2. 仕様の矛盾はAI実行ではなくVALIDATED失敗として返る。
3. AI実行環境から資格情報・GitHub管理操作・PR作成を行えない。
4. 未許可ファイル、生成物、秘密情報はPR作成前に停止する。
5. task_idから承認者、モデル、利用回数、検査結果を追跡できる。
6. 実装者と二重レビュー担当者の独立性を機械的に検証できる。

## 非目標

既存Actionsへ条件を継ぎ足して延命すること、または監視サービスに自動修復や強権限を与えることは、この再設計の対象外とする。
