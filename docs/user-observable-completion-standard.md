# 利用者観測可能な完了基準

## 目的

DevFlowでは、内部ジョブ、ログ、ポーリング、HTTP応答が存在することをもって機能完了としてはならない。
完了とは、依頼した利用者が、指定された入口で、指定された結果を確認できることである。

この基準は、実装者、レビュー担当、承認者、運用担当が同じ完了根拠を使うための必須基準である。

## 最初に固定する一文

実装を始める前に、依頼ごとに次を一文で記録する。

> **誰が、どの入口で、何を、いつまでに確認できれば完了か。**

内部コンポーネント名や実装手段は、この一文の代わりにしてはならない。

例:

> 承認済みDevFlowタスクが実行中である間、Orcaの利用者は2分以内に、Issue番号・タスクID・現在状態・観測時刻を確認できる。

## 到達経路の証明

利用者へ見える結果を作る変更には、PR本文または設計記録に次の到達経路を記載する。

```text
状態の発生
  → 永続記録
  → 配信の登録
  → 配信先での受信
  → 利用者が見る表示
```

各矢印には、責任を持つコンポーネントと検証方法を対応させる。いずれかが「後で行う」「自動的に届く」など曖昧な表現なら、設計未完了として実装を開始しない。

## 禁止する代理指標

次の事実だけでは、利用者機能の完了根拠にならない。

- 定期実行の設定や `sleep` が存在すること
- HTTPエンドポイント、ログ行、Firestore文書が存在すること
- 内部状態が更新されること
- 実装者が作った文字列検索だけのテストが通ること
- 「通知する」「再開できる」と出力文に書かれていること

これらは内部実装の補助証拠にはなり得るが、利用者に届くことの証明にはならない。

## 必須の完了証拠

利用者に結果を報告する機能は、少なくとも次を提示する。

| 対象 | 必須証拠 |
| --- | --- |
| 実行中の報告 | 利用者が見る入口で、指定間隔以内に観測できたメッセージまたは状態画面 |
| 終端報告 | PR URL、差分なし、失敗コード、期限切れなどの終端結果を一度だけ観測した記録 |
| 再起動・再開 | 同じタスクIDを再取得し、重複せずに最新状態を確認できた記録 |
| 停止 | 終端後に新たな定期報告が出ないことを確認した記録 |
| 配信障害 | 配信先を利用不能にしたとき、定めた時間内に利用者へ監視異常が見える記録 |

「通知した」と報告する場合は、通知IDまたは受信時刻・表示先を含む証拠を添える。証拠がない場合は「未確認」と表現する。

## 独立検証ゲート

実装者とは別の担当が、実装コードではなく利用者操作から確認する。

1. 利用者の入口から依頼を作成する。
2. 承認後、指定間隔内の実行中報告を少なくとも2回確認する。
3. PR作成、差分なし、失敗、または期限切れのいずれかの終端報告を確認する。
4. 再起動または再接続後に、同一タスクの最新状態を確認する。
5. 終端後、定期報告が止まることを確認する。

このゲートは単体テスト、構成テスト、CI成功と置き換えられない。どれか一つでも利用者の入口で観測できなければ不合格とする。

## 反証テスト

各利用者向け経路には、到達経路の一部を失わせる試験を用意する。

例えば状態保存だけが成功し、Orcaへの配信が失敗する場合、指定時間内に「配信・監視異常」が利用者へ見えなければならない。内部ログだけに残る状態は不合格とする。

## レビュー時の確認事項

- 利用者が最終的に見る入口は具体的に何か。
- 状態発生から表示まで、未実装の矢印はないか。
- その入口を実際に見た証拠はあるか。
- 実装者自身のテストだけで合格にしていないか。
- 配信不能時に、沈黙ではなく可視の失敗になるか。
- 再起動、重複起動、終端後の停止を確認したか。

## 表現の規則

「完了」「通知済み」「安全に再開できる」といった表現は、上記の必須証拠が揃った場合に限る。
証拠が一部だけなら、実装済みではなく「内部状態は確認済み、利用者到達は未確認」と明示する。

## 変更時の適用

利用者向けの状態、通知、承認、実行、復旧、完了表示を変更するPRは、この文書への適合をPR本文に記載する。適合しない場合は、理由と暫定的な制限を明記し、利用者機能の完了としてマージしない。
